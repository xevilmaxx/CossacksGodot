## 2. Why a green quad instead of a transparent building

1. **The ghost is literally one flat box, not a building mesh.** `_ensure_roots()` creates `BuildGhost3D`, sets `_ghost_mat = _material(GHOST_OK, false)`, constructs `BoxMesh` with `size = Vector3(1.0, 0.05, 1.0)`, wraps it in a single `MeshInstance3D` named `Footprint`, and assigns `material_override` (`variant3d/scripts/world3d_fx.gd:779-791`, box at `:785-786`). `draw_ghost()` never instantiates another node; it only rescales that box by `_building_radius(sid)` (`variant3d/scripts/world3d_fx.gd:583-584`, radius helper `:1419-1424`). OBSERVED. Conclusion: the visible "quad" is a 5 cm-high footprint stand-in (DERIVED). This is already described in the carried report as a "translucent green/red footprint box" (`DBUILD_01_building_stages.md:170`, `:243`).
2. **The real building mesh is never instantiated for the ghost.** In FX there is no OBJ/GLB load, no stage mesh and no `MeshInstance3D` beyond the box (whole module `variant3d/scripts/world3d_fx.gd`; creation site `:779-791`). By contrast live buildings get their mesh in `world3d_entities.gd:1622-1663` (`_mesh_info` at `:1637`, `MeshInstance3D` at `:1638-1640`) and stage-0 art is resolved by `_stage_mesh_info()` at `:1796-1821`, with converted stage OBJs reported at `:275-277`; stage 0 maps to suffix `"1"` at `:1782-1788` (donor `floor(progress*4)` in `DBUILD_01_building_stages.md:81`). OBSERVED / DERIVED. The stage-0 building geometry is simply absent from the ghost branch (INFERRED as the direct cause of the owner's complaint).
3. **Transparency is not actually missing.** `GHOST_OK` is `Color(0.20, 1.00, 0.30, 0.45)` (`world3d_fx.gd:141`), `_material()` sets `TRANSPARENCY_ALPHA`, unshaded lighting, emission and `CULL_DISABLED` (`world3d_fx.gd:874-885`), and `_update_ghost()` multiplies alpha by a 0.85..1.0 sine pulse, giving an effective alpha ≈0.38..0.45 (`world3d_fx.gd:1363-1367`). OBSERVED / DERIVED. So the defect is **shape/art**, not an opaque green overlay. If a real mesh is added, note the ghost material currently does **not** set `depth_draw_mode = DEPTH_DRAW_DISABLED`, unlike the snow/impact materials (`world3d_fx.gd:846`, `:903`) — self-occlusion of a multi-face building mesh is a possible follow-on issue (INFERRED).
4. **Validity tint is already wired.** `ok` comes from `can_place(...).ok` plus affordability in `variant3d/scripts/world3d.gd:491-497`, is stored in FX at `world3d_fx.gd:575`, and the green/red choice is made at `:1363` from constants `:141-142`. OBSERVED. Donor ghost colour/size is UNVERIFIED — no donor config defines it (`DBUILD_01_building_stages.md:166-168`), so no donor-colour parity claim is possible.
5. **The half-map offset is not currently producing a 320 m-misplaced ghost.** The live handoff supplies SIM metres (`picking3d.gd:121-122`, `:235-243` → `input_controller.gd:1348` → `world3d.gd:784-786` → `:425-426`), and FX subtracts the same half-map when placing the node (`world3d_fx.gd:690-699`, offset `:407-415`), matching the entity transform (`world3d_entities.gd:1494-1513`). The fallback path adds the half-map to the centred camera hit first (`world3d.gd:431-436`). An earlier measured probe put the ghost at the cursor with 0.000 m / 0.000 px delta (`PLAY2FIX_ghost.md:150-158`). OBSERVED / DERIVED. Live F2 ordering remains UNVERIFIED (`PLAY2FIX_ghost.md:170-175`).
6. **Blink is only a generic pulse.** `world3d_fx.gd:1364` uses `sin(_time*4.0)`; the donor expectation carried in `DBUILD_01_building_stages.md:162` is a canbuild/cannotbuild blink mode with appearance UNVERIFIED at `:166`.
