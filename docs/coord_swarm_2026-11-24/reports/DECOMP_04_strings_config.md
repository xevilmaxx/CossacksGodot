# 1. Scope and method

Target: `C:\Games\Cossacks 3\cossacks.exe` (5,768,048 B, SHA-256 `87f0f3c130b0…e16c`), already-open Craft Anything target `t_87f0f3c130b0`. No target was opened or selected by this agent; no donor code was run; nothing was unpacked; no source/asset/git file was touched.

Three search layers were used, and **they disagree** — this is the main finding of this audit:

| Layer | Tool | What it really searches | Consequence |
|---|---|---|---|
| Data-section strings | `native_strings_find` | Only strings stored in **data sections** (`.rsrc`, `.idata`, `DATA`). Its own limitation code is `data_sections_only`: *"only strings stored in the file are searched (absence is not proof)"*. | Returned **0** for `SphereHeight`, `SphereHeightMin`, `MinHeightMinAngle`, `FocalLength`, `DynFogDepth`, `Weather`, `DateTimeEnable`, `grass1`, `sand`, `rock`, `diffusewaves`, `hmapTex`, `terrainmesh`, `.map`, `.hmap`, `.dds`, `.tga` — **all false negatives** for "is this token anywhere in the binary?". |
| Whole-file byte search | `native_bytes_find` | Every byte of the file, UTF-8 **and** UTF-16LE, with virtual address + containing section for mapped bytes. Limitations: `file_bytes_only` (packed/encrypted regions and runtime-built strings are not seen) and `unmapped_regions`. | Found most of the "missing" config keys as ASCII byte strings **inside the `CODE` section**. | String → code linking | `core_feature_find`, `native_xrefs_list`, `native_function_find` | String table → functions/imports/xrefs, constrained by the same incomplete function recovery noted in DECOMP-01 (6,000,000-instruction stop, 1,238 unresolved indirect jumps). | All probed class names returned **0 functions, 0 imports, 0 involved functions**; one config key (`SphereHeight` at `0x7abc44`) does have a single data xref from `sub_7ab704` (`ev_01a2cde3…`), but `hmapTex` at `0x853e0c` has no xref and is "not inside a known function" (`ev_ef7f2203…`, `ev_e2ec6c6d…`). |

Supporting views: `native_strings_browse` over all 4,090 `.rsrc` strings (`ev_c8e8bca6…`) recovered the Delphi unit/RTTI neighbourhood; `native_data_show` confirmed that the leading punctuation on some `.rsrc` strings is a prefix byte, not part of the name — e.g. `0x9593b3` is `u8` `60` (0x3C, "`<`") and the cstring at `0x9593b4` is exactly `XTerrainBorders` (`ev_8d732651…`, `ev_f3fef60d…`); likewise `0x958c10` is `u8` `36` (0x24, "`$`") and `0x958c11` is exactly `XWaterShader` (`ev_aaa3dc9f…`, `ev_e94ef200…`). All addresses below are virtual addresses; file offsets are given where the byte-search tool supplied them.

**Status definitions used below**

- **PRESENT** — exact token occurs as bytes in the file (any section, UTF-8/UTF-16LE).
- **ABSENT-FROM-BINARY** — zero byte occurrences in the whole file. This is *not* proof of disuse: the file may be packed/compressed at rest, names can be built at runtime, and the values themselves live in external `data/**` text files.
- **UNVERIFIED** — a hit exists but its role cannot be established statically (RTTI/metadata vs live config lookup), or the exact token is absent while a close variant is present.

# 6. Interpretation — where donor terrain behaviour actually lives

1. **The keys are in the binary, but not in the string table.** `SphereHeight`, `SphereHeightMin`, `MinHeightMinAngle`, `FocalLength`, `DynFogDepth`, `Weather`, `DateTimeEnable`, `hmapTex` and `.map` are all present as UTF-8 bytes in `CODE`. DECOMP-01's "0 matches" for these tokens came from a data-sections-only string scan, not from their absence. This is the single most important correction from this audit. CODE-resident strings in a Delphi program are typically constant pools or text embedded with the compiled script/data; a few show real data xrefs, but function recovery is incomplete, so their exact use stays UNVERIFIED.
2. **The engine's terrain/appearance type vocabulary is in `.rsrc` metadata.** The Delphi unit/RTTI table gives `EXTerrain`, `XTerrainDataLite`, `sXTerrainData`, `XTerrainBorders`, `XTile`, `XTileSeason`, `XCliff`, `XSeason`, `XWorld`, `XMap`, `HXHeightField`, `XColorTable`, `XSkyDome`, `XEnvironment`, `XWater`/`XWaterShader`, `XClouds`, `XHorizonRender`, `OSWAtmosphere`, `XAir`, `XStars`, `XPHDR`, `XShadowMap`, `XLightShader`, `XMapGenerator`, `XMapCover`, `OSWTexture`/`OSWTextureCombiners`/`OSWProcTextures`. So the donor engine definitely has heightfield, colour-table, sky-dome, water-shader, cloud, season and texture-combiner abstractions — structurally consistent with our heightfield direction, but this is metadata, not decompiled behaviour.
3. **The concrete data is external.** The absent terms are exactly the ones that would be *values/filenames*: `grass1`, `sand`, `rock`, `diffusewaves`, `terrainmesh`, `.hmap`, `.dds`, `.tga`, `water.dev`. Near-misses (`grass`, `Diffuse`, `wave`, `hmapTex`, `xdds`) show that the binary knows the *words* but not the *asset names*. Those names must be in `data/**` scripts/configs, which no binary string search can see.
4. **Therefore: do not infer disuse from a zero-match.** A key absent from `native_strings_find` may still exist in `CODE`; a token absent from the whole file may still be a live key read from an external text file at runtime. Both absence classes are documented as observations about bytes only. The tools themselves report `data_sections_only`, `file_bytes_only` and `no_match` with "absence is not proof".
5. **Limits:** no function was decompiled; no xref chain was resolved beyond one `SphereHeight` data reference *(superseded by section 8: `sub_7ab704` was studied and shown to consume `SphereHeight`, `SphereHeightMin` and `DynFogDepth` as config look-up keys);* the `.bind` packing heuristic from DECOMP-01 is untested here (`core_packed_files_list` returned `not_supported` — "This file doesn't carry files in any way we recognise"; no evidence id because the call failed). No runtime unpacking, Frida, execution or asset extraction was performed.
